# 多句样本校准：第一阶段候选

## 目标与范围

在已经能取得有效 Hook 正文的 Windows 游戏里，通过截图测量规则字格、人工确认覆盖关系来校准透明查词层，降低逐引擎读取真实字形位置的适配成本。首个用户验收对象为 Little Busters! EX（REALLIVE）；沿用已有文本、语音链路，不新增游戏 Hook、不更改语音归属，也不引用此前未合并工作区的实现。

当前候选提供完整客户区截图与当前 Hook occurrence 的采集、多句本机草稿、自动测量与 native 点击框预览，以及不参与拟合的验证样本。早期人工中心标记与 DirectWrite 字体排版作为高级手动路径保留。最终应用仍进入既有实时校准与点击探针确认流程，保存样本草稿本身不会开启查词。下文早期工程记录保留历史事实，第六轮记录当前实现与验证。

## 已冻结的参考契约

基线为个人正式线 `custom@6016606103`，参考的是当前 checkout 已有贴附层，不把其他游戏的引擎几何能力外推到 REALLIVE。

| 环节 | 实现与边界 |
| --- | --- |
| 文本 | `GalHookTextOverlayController` 的既有 selected session / body thread / latest entry；采集前后必须同 session、occurrence、seq、thread、正文及 HWND。重复同文不靠字符串单独认定同一事件。 |
| 几何 | `attached_text_surface_window.cpp` 原 `RebuildClusters` 的 DirectWrite 排版，抽成 `attached_text_layout.h` 唯一实现；离线预览与实际 surface 调用同一实现。 |
| 坐标 | 原始截图客户区 physical px → UI 等比显示/缩放；锚点存客户区归一化坐标。正式贴附层仍按其原有 body-local 整数取整，再平移回 client；不额外乘 DPI。 |
| 输入 | 本阶段采集与预览不创建或武装输入面。应用后使用既有整簇 hit、点击 down/up 盾、Shift hover、公共 popup 与制卡链。没有新增游戏快捷键。 |
| 截图 | 复用 WGC `captureWindow`，新增可核验 metadata。只接完整稳定客户区；Magpie 重定向、尺寸不符、缺元数据或裁剪失败均拒绝。 |
| 生命周期 | 明确因 `targetBackground` 隐藏的稳定会话允许采集；未知挂起、实时校准草稿、最小化、换游戏、换线程、换句或捕获期间尺寸变化均拒绝。旧 surface 使用已有精确 token 截图屏障并在 finally 恢复，新档案无 surface 时不伪造 lease。 |

以上为 `source-confirmed`；自动化和真实游戏证据分别记录，不把它升级为 `real-game-tested` 或 `user-accepted`。

## 使用流程

1. 用户按平时方式转区启动游戏，连接既有 Hook 并选择正确正文线程。关闭自动播放/快进，停在完整显示的台词。
2. Fushi 台词工作台选“仅贴附层”，打开“多句样本校准”。点“采集当前台词”。可切回游戏推进一句，再切回样本页采集；不需要重复注入。
3. 已存样本可以继续使用，最多八句。至少一个训练样本须有完整的自然换行台词；自动对齐共同使用训练样本，保留用户指定的验证样本。切换当前查看的图片不会改变训练/验证分组。已有两行、三行样本时无需重采。
4. 检查每张截图与 Hook 正文相符且已经完整显示。在“拖动外框”模式拖动橙色外框内部以平移，拖动边缘/角落的方块改变区域宽高。右侧数值以原始截图像素表示，可输入后回车，或点加减按钮；区域高度不等于字号，单行文字没有触及底部时，增高区域不会放大字框。
5. 大致框住所有正文，避开人物名字和按钮；点“从截图自动对齐”。程序从截图测量位置、字距、行距和换行/缩进，无需标记字符中心或输入字体参数。无法可靠求解时保留原草稿，记录提示后统一反馈。
6. 成功后检查每一行的开头、中部和结尾：框应包含对应的字，第二行不能整体错一格。再切换已有短句看覆盖关系；检查的是可点击区域，不要求字形居中到像素。自动字格模式隐藏无关的字体/中心标记控件。
7. 默认尚未自动对齐时只显示选区，不生成旧字体的蓝框或显示字号溢出提示。手动字体排版仍保留旧的标记与拟合路径，可通过“手动排版（高级）”显式切换；本轮自动对齐验收不要求使用它。旧路径中的 px 数值只是人工点与框中心的 RMS 偏差，不代表真实几何精度。
8. 保存草稿，或选择“将草稿用于游戏校准”进入实时三点探针确认。切回游戏后只有输入链就绪才显示框；按提示依次点击对应字符的小字框内部，记录成功的框变绿。大区域外框不是整块点击屏障，字框外仍保留游戏原行为。区域调整在样本截图页完成；实时游戏层不再支持拖动大框。切回 Fushi 确认观察到的三个字符后提交，再验证查词。

## 手动拟合历史与存储边界

下面前两条描述保留的人工拟合路径；当前自动字格路径见第四轮，使用截图笔画分布测量，无需人工中心点。

- 不使用生产 OCR、截图文字识别或 AI 猜测坐标。人工提供已知文字对应的点；有限差分与最小二乘只用于 position/tracking，native 再验证候选。至少六个训练点时，用中位数斜率/平移初始化并按残差加权，降低少量误点的影响；不会删除标记，UI 偏差仍计算所有标记。该方法不能消除一致方向的人工偏差或错误字体造成的系统偏差。
- 至少需要同一行上两个分离的字簇。若微小字距扰动改变标记字的行、拟合导致换行/溢出或误差变差，则拒绝该次拟合，不覆盖原参数。
- 两点只能粗略估计位置和字距，无法判断哪个点不准；增加训练点也不能替代留出句和实际查词验证。已有本机草稿继续可读，无需重新采集全部截图。
- 字体未知、特殊禁则、注音、不同对白框、游戏重新排版、黑边及 Magpie 缩放仍需独立验证。客户区按比例缩放不是所有分辨率自动准确的承诺。
- Hook occurrence 稳定只能证明取样期间文本身份未变，不能证明游戏逐字动画已结束；用户必须检查截图。无法据此声明精确引擎字形。
- 草稿位于 app support root 的 `gal_lookup_calibration/<exe-sha256>.json`，只存本机；最多八张、单图 12 MiB、全部图像 64 MiB，文件加载上限 92 MiB。样本含游戏画面和正文，不写日志、源码、共享 profile 或上传。
- 不修改数据库 schema。第四轮在 profile 中增加严格校验的可选 `layout.cellGrid`，旧 profile 缺少该字段时沿用原字体排版；旧版本无法正确消费新增字格，不能将旧 EXE 当作新候选验收。草稿丢失不影响已有查词设置；运行期 profile 仍由已有校准提交流程保存。

## 一次真机验收

本轮源码位于 `codex/lookup-calibration-samples-20260917`，独立 worktree 为 `.worktrees/lookup-calibration-samples-20260917`。按用户指定，由用户双击该目录已有的 `启动Hibiki最新版.bat` 完成 Windows x64 本地构建。BAT 以自身目录定位源码，自动准备依赖、构建并启动 `fushi/build/windows/x64/runner/Release/fushi.exe`，无需 `clean` 参数。该入口用于本地功能验收，不等同于完整发行包验收。

第一步只验证本轮代码能构建且 Fushi 能打开；成功后再按平时转区方式启动测试游戏。若 BAT 报错，停止游戏验收并保留命令窗口末尾输出；构建日志就在该命令窗口，脚本不会自动保存完整日志。代理不代替用户启动应用、游戏或执行此 BAT。

目标是验证“少量样本校准后，新句仍可命中”，不是只调准截图。

| 场景 | 成功标准 | 失败停止条件 |
| --- | --- | --- |
| 稳定截图 | 图像恰为游戏客户区，正文与 Hook 相符；切回 Fushi 仍可采集 | 错图、边框混入、错句或截取失败：停止标记，保留当前画面 |
| 区域与标记编辑 | 拖底边能看到橙色区域高度变化，字号不随之改变；放大后仍能拖框、拖标记，方向按钮每次移动一原图像素 | 框不动、跳位或标记被误改：保存草稿，停止应用 |
| 多行自动对齐 | 选中完整多行图，大致框正文后自动生成字格，各行首尾对应 | 自动求解拒绝、错字或框溢出：保留草稿，停止应用 |
| 留出句 | 未参与拟合的句子也有合理点击框 | 长句累计偏差或换行不符：不应用，记录失败样本 |
| 后续新句 | 实时校准后连续约十句，点字查到对应词；空白保持原游戏行为 | 点错字、点字推进台词、弹窗操作穿透：立即关闭贴附层 |
| 窗口变化 | 如游戏提供普通窗口缩放，在第二个尺寸重新采集验证 | 黑边/重排版导致错位：维持已验证尺寸，不宣称跨尺寸通过 |

普通运行日志通过 Fushi 现有日志入口取得；校准证据以本机草稿为准。用户报错时先提供阶段、样本编号及现象，真实截图/正文仅在本机诊断。未完成本表前状态为候选待验收，不合入 `custom`、不推送。

## 第四轮：截图测量字格与查词恢复

源码与定向测试提交为 `88bf7d6d93`，仍在 `codex/lookup-calibration-samples-20260917`；目标候选为同一 worktree 的 Windows x64 本地构建，真实游戏验收状态为 `implemented_unverified`。

用户完成一批体验后统一授权修改。旧中心点拟合只解平移和字距，无法自动解决字号、换行和续行缩进。现增加“从截图自动对齐”：用户大致框住正文，选一张完整多行图，由本机在后台测量笔画分布，与已有 Hook 正文对应。人工只确认各字落在对应框内，不需要点击字符中心或输入字体参数。选中样本用于求解，其余已存样本用于独立检查；失败保留原草稿。

这一路是 `attached_calibrated` 的规则字格近似，非 exact engine geometry，也不进行 OCR。截图只用于校准，游戏运行时只依据当前 occurrence 的正文与已保存字格布局生成命中框。预览和运行复用同一 native `Build`；字格模式包含字格宽度、行高、行距、软换行列数、普通/引号开头台词续行缩进。全角空格占位但不产生命中；不支持的字符与溢出拒绝发布。旧 profile 没有 `cellGrid` 时继续原 DirectWrite 路径；未知/坏字格字段不静默降级。

要求至少一张有软换行的两行或三行样本：短句只能测出字距，无法证明一行容纳多少字。显式换行但列数不确定、多解、背景干扰、比例字体、注音或不规则排版不在本轮可靠求解范围，未通过检查时拒绝自动应用。图像行和列的误差检查只证明样本与模型吻合，不代表新句、其他尺寸或其他游戏已经验收。调查初期的三张已存图均为单行，最后离线检查时已有六张短句；未改写这些草稿，也未把聊天截图存入应用。
