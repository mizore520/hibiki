## 必须保持的行为

以下是保护与验收要求，并非宣称当前实现已全部通过：

- 复用已经能够取得的 Hook 文本与语音，不为视觉定位问题重写获取链；文本、画面与点击必须属于同一次当前台词，不能混用上一句或相同字符串的另一次事件。
- 自动拟合失败保留已有草稿和样本；单个样本出错要指明具体样本与可核对原因，不能把错误统一推成“用户框不准”。
- 成功的 Little Busters 样本作为回归依据，同时保留新游戏失败样本。旧样本通过不能证明通用适配成功。
- 字符索引、坐标变换与输入所有权要一致；点字查词不应推进游戏，弹窗关闭后能再次查词；不能靠延迟、吞异常或放宽命中门槛遮掩问题。
- 训练与验证样本保持各自用途；测试、预览、实际查词的布局契约一致。不能只改预览让界面“看着齐”。
- 游戏间配置隔离；失败不能删除用户校准数据；改变分辨率时区分整体缩放与重新换行。

## 当前已知问题和解释边界

详见 [集中反馈清单](gal-lookup-feedback-20260918.md)。目前有验证后闪退、跨游戏正文行检测失败、字符范围限制导致整批拒绝，以及明明两行却提示缺多行等问题，均未完成本轮修复。

三点容易误读：样本 4 显示时可能报样本 3 的错误；“无法验证字符宽度”实际可由字符范围检查提前触发；“需要多行”可能覆盖另一检测分支的失败原因。不能据此认定用户没有正确操作。

现有截图算法是固定字迹阈值与横排规则字格拟合，没有验证通用兼容性。OCR/成熟文字检测属于待比较路线，尚未选型、引入或验证准确度；已有 Hook 不构成排除 OCR 辅助定位的理由，也不能把 OCR 行框当作精确逐字框。方案评估与引擎直接提供字形的能力声明必须区分；现有生产查词规则与守卫如受影响，应明确说明需求和契约变化，不静默删除守卫。

## 每批改动的交接格式

开始时简述：本批修什么 → 根因证据 → 预计修改范围 → 必须保持的行为 → 定向验证。普通实现直接在授权范围内继续，不让用户审批每一个步骤。

结束时记录：提交与实际 diff → 真实执行的验证及未通过项 → 已保留的旧行为 → 未解决问题 → 用户下一次唯一的体验批次。关键链路在交付前集中独立复核。用户决定采用前保留候选；不自行合入 `custom` 或推送。

需要取回旧代码时，从检查点另建恢复工作区进行对比，不在脏工作区执行 `reset --hard`、批量 restore 或清理。数据库与校准样本的恢复另核对备份，不能由源码检查点推断。

换模型时可直接发送：
