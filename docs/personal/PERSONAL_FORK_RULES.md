# Fushi 个人版本长期工作规则

## 1. 项目定位

- 本仓库是 Fushi（原 Hibiki）的 Windows 个人版本，不是对上游产品路线的替代。
- 长期目标是同时保留两类价值：作者持续提供的公共更新，以及用户按个人习惯定制的功能。
- 保留的是用户需求、数据和使用体验，不要求永久保留个人实现。若上游后来提供等价或更好的实现，应优先复用上游并缩减重复代码。
- 上游技术规则、真实代码路径和当前能力会持续变化；开始任务时必须以当前仓库为准，不得只按旧任务书、聊天记录或记忆判断。

## 2. 规则分层与冲突优先级

1. 系统、开发者和用户当前明确指令始终优先。
2. 根 `CLAUDE.md`、`docs/agent/` 及子目录规则负责技术、安全、构建和测试约束。
3. 本文件负责个人版本的分支角色、需求边界、候选验收、上游同步和发布授权。
4. 若作者规则要求“小改默认合并”，但本文件要求候选验收，则个人正式线的验收门优先：未经用户明确确认，不得合入 `custom`。
5. 若个人需求与作者的技术硬规则冲突，先报告冲突；不得为了完成需求绕过数据、安全、测试或平台边界。

不要把本机密钥、私人服务器、远程设备、私人游戏路径或数据目录写入本文件；这些信息只放在被忽略的 `CLAUDE.local.md` 或其他本机私密配置中。

## 3. Git 与工作区职责

- `upstream/develop`：作者更新来源，只允许获取和读取，不向 `upstream` 推送。
- `custom`：个人正式整合线，正常情况下保持干净，不直接在其中开发。
- `origin/custom`：个人正式远端线。只有完成验收和合并后才推送。
- `codex/<任务名>`：单项功能、修复、调查落档或上游同步分支。
- 所有代码、文档、配置和测试改动都在独立 worktree 中完成，并遵守根 `CLAUDE.md` 的初始化要求。
- 创建任务前检查主 checkout、目标分支、远端、未提交文件和现有 worktree；不得覆盖、清理或擅自提交用户已有改动。
- 不反复 rebase、不改写 `custom` 历史、不 force-push。作者更新通过专门同步分支合并进入个人线。
- 官方内置更新器只能更新作者发布的软件包，不能合并个人源码；个人版本通过 Git 同步源码后重新构建。

## 4. 标准工作流程

一项新想法依次经过以下状态：

1. **理清需求**：先确认实际问题、理想体验、范围、非目标和可观察的验收标准，不急于修改仓库。
2. **仓库调查**：Codex 核实当前实现、上游重叠、数据风险和可复用能力；外部整理的需求不代表技术事实。
3. **阶段实施**：在独立 worktree 完成一个可单独体验的小阶段。
4. **工程验证**：执行与爆炸半径相称的格式、分析、自动测试和构建。
5. **候选验收**：用户使用候选 EXE 和真实案例验证用户可见行为。
6. **正式采用**：用户明确授权后合入 `custom`，构建正式版并按授权推送 `origin/custom`。

若需求与真实代码冲突，先报告差异并由用户决定产品目标；不得静默改变需求，也不得为了照搬外部描述而忽略现有架构。

## 5. 大型功能的拆分

- “完整游戏管理器”“统一查词与制卡”等大型方向只作为长期主题，不能直接成为单个无限实施任务。
- 按用户可以独立体验和验收的能力拆阶段，而不是按文件数量机械拆分。
- 每个阶段必须有独立范围、非目标、真实案例和候选版本。
- 大型主题可保留一个总方向；每个阶段使用单独范围、分支和 worktree。
- 长期分支只在确有分阶段审查需要时保留。已完成且通过的阶段及时进入个人线，避免半年后一次性处理巨型冲突。

## 6. 与上游重叠的处理

开始实现前检查作者是否已经实现、正在重构或计划相同方向。按以下顺序处理：

1. 上游已经完全满足需求：采用上游，删除或不再新增重复实现。
2. 上游基础更好但缺少个人行为：复用上游，只保留薄的个人扩展。
3. 双方各有优点：复用上游底层，合并用户需要的体验，不长期并列维护两套系统。
4. 目标确实不同：才保留个人实现，并优先做成独立服务、adapter、策略或设置项，减少侵入公共核心。

通用且适合所有用户的改进，可以先询问用户是否愿意向作者贡献；不得自行创建上游 PR 或进行外部发布。

作者刚进行大型重构或正在频繁修改的区域，先完成只读调查和范围确认。除非用户明确要求，不在尚未稳定的核心区域立即展开跨数据库、导航、全局状态和多个页面的巨型改造。

## 7. 实施与验证边界

- 先沿真实代码和数据路径调查，再修改；不得凭旧文档或名称猜实现。
- 优先根因修复和小范围扩展，不复制整个页面或核心模块只为保留少量个人差异。
- 用户可见行为必须用用户报告的真实案例验证；自动测试不能替代真实体验。
- 自动测试通过只代表工程门通过，不代表候选验收通过。
- 用户可见的 Windows 代码改动完成后，交付独立候选 EXE，并清楚标明来源分支、提交和测试结果。
- 纯文档或规则改动不要求候选 EXE，但仍需用户审阅并明确授权后才能进入 `custom`。
- 候选失败时继续在原任务分支调查和修改；不得把失败版本合入正式线，也不得用新的猜测补丁掩盖真实原因。
- 涉及用户数据时先确认迁移、备份、降级和恢复行为；不得通过修改 schema 或绕过版本守卫强行打开旧数据。

## 8. 合并与推送授权

以下表达只代表继续候选修改，不授权合并：

- “再改一下”；
- “看起来差不多”；
- “自动测试通过了”；
- “先给我试试”；
- “候选版不通过，继续修改”。

只有用户明确表达下列同等意思时，才授权合入个人正式线：

> 候选版测试通过，可以合并到 `custom`。

推送和正式构建属于合并后的独立动作。只有用户明确要求“推送”或任务书已清楚授权完整发布流程时，才推送 `origin/custom`。禁止向 `upstream` 推送。

文档和规则改动使用同样的明确确认门，但以用户审阅文档代替 EXE 验收。

## 9. Windows 与第三方项目边界

- 个人版本的主要使用、候选交付和正式构建目标是 Windows；除非用户明确改变范围，不为个人功能额外扩展其他平台。
- Galgame 文本/语音 Hook、LunaHook、helper、adapter、引擎适配和制卡 E2E 严格遵守根 `CLAUDE.md` 的 Windows-only 硬规则。
- 参考 ReinaManager 等第三方项目时，可以借鉴用户体验、信息结构和业务规则；复制代码、资源或数据前必须由仓库可见 Codex 核对许可证、技术兼容性和分发义务。

## 10. 每次任务的交付说明

最终回复至少说明：

- 本轮完成和未完成的内容；
- 改动所在分支与 worktree；
- 实际运行的验证及其结果；
- 未运行或被环境阻塞的验证；
- 候选版位置（若有）；
- 当前是否尚未合并、尚未推送；
- 需要用户作出的下一项决定。

不得把“代码已写”“测试已绿”“构建成功”描述成“用户已经验收”或“正式版已经采用”。
