# Fushi 个人工作规则

本文件只保存长期协作约定。技术实现和强制验证由根 `CLAUDE.md`、`docs/agent/` 及对应模块规则维护；当前进度、截图、命令输出和验收结果放在任务记录中。

## 1. 范围与优先级

- 这是 Fushi（原 Hibiki）的 Windows 个人版本：保留作者更新与个人需求，优先复用现有实现。上游有更好的等价能力时，缩减个人重复代码。
- 系统、开发者及用户当前明确指令优先。作者规则负责技术、安全、数据、平台与必要验证；本文件负责协作节奏、分支职责和个人正式线的采用授权。
- 作者的“小改默认合并”“验证后 push/PR”不授予本项目合并或发布权限，按第 7 节执行；无需为这个已明确的差异重复询问。真正无法同时满足的约束才向用户说明冲突并请求决定。
- 以当前源码、配置和可核验证据判断事实。旧聊天、任务书、文档中的行数/版本不能代替现场核对。先查与任务相关的本地和已知上游能力，只有缺少必要信息时才扩大调查。
- 个人交付默认限 Windows，Galgame 严守作者的 Windows-only 规则。引用第三方实现须核实许可证与分发义务。密钥、私人路径、游戏素材及远程设备信息只放被忽略的本机文件，不进入规则、源码或公开报告。

## 2. 先识别用户正在做什么

| 用户意图 | 代理行动 |
| --- | --- |
| “解释一下”“先理解需求”“不要做工作” | 用大白话解释；允许时做必要只读调查，不改源码、不跑构建。 |
| “先记下”“全部测完再一起解决” | 在当前任务的同一问题清单中记录现象、预期和证据，待本轮体验结束后统一归因；不逐条开工。 |
| “开始改”“帮我做好”或明确的行动请求 | 将目标转成可检查结果，完成必要调查、实现、定向验证与本地提交，不反复确认普通实现细节。 |
| 工作期间补充意见或询问进度 | 纳入当前任务，简短回应后继续；只有明确取消或目标不兼容时才替换原任务。 |

信息不足时先推进不依赖答案的部分。能根据上下文合理确定的可逆细节直接决定；关键产品目标、数据风险或授权边界缺失时才提一个具体问题。授权在同一会话内持续有效，不因重试、换模型或上下文整理而失效。

## 3. 按批次交付

通常按“集中体验 → 汇总问题 → 核实根因 → 统一修改 → 必要验证 → 一个候选”推进。体验中先在同一清单记录现象、触发步骤、预期、证据与状态；统一调查后按作者的 `tool/bug.dart` 流程登记，未复现的也如实标注，不把猜测标成已复现。

- 普通对齐、文案或易用性反馈不立即打断体验。阻断后续测试、错误输入、数据损坏等问题先说明影响；只在已授权范围内优先处理，用户明确只记录时不擅自改代码。
- 大任务按用户可体验的能力拆阶段；每阶段有清晰目标、验收场景和结束条件。候选失败继续在原任务分支修，不为每个问题另起工作区。
- 不靠延迟、重试、吞异常或游戏特例掩盖根因。已定位的问题修在实际数据、状态、生命周期或契约边界。
- 同一批代码完成定向验证后再交用户构建。用户集中反馈，代理统一处理；不要每修一行就要求重编、重启或重新附着。

## 4. 模型分工与额度

- 适合独立开展的文件定位、资料整理、常规实现、测试执行、格式及文档检查，优先交给 **`gpt-5.6-luna`，`max`**。主代理负责关键判断、根因、设计、整合和必要复核。
- Luna 因服务不可用等环境错误失败时，可直接改用 **`gpt-5.6-terra`**，思考强度按任务选择，不必重新问用户。代码断言失败不属于换模型的依据，应先检查事实。
- Luna 恢复后用于后续适合的任务；已经工作的 Terra 代理让它做完。不要为换模型中断、重派或重跑已完成工作。
- 只有边界清楚、能独立推进且主代理同时有事可做时才派发。几行修改直接完成；不要为“使用子代理”制造任务或多层转派。同一文件和同一验证只交一个执行者。
- 给子代理足够的目标、文件范围、规则与验收标准，不发送无关完整历史。回传真实命令、退出码、执行数量及关键证据，主代理核对结果，不把相同工作全部重做一遍。
- 工作模型、子代理模型与自动审批服务分开看待，不宣称已更改工具未提供的设置。503、审批超时或环境故障不能靠无限重试解决；有新证据或环境变化再重试，否则保留进度、完成未受阻工作并说明具体阻塞。不得绕过审批。

## 5. 验证做到必要且有效

| 改动类型 | 本地验证 |
| --- | --- |
| 纯文档、规则、注释 | 检查内容、相互引用、相关链接与 `git diff --cached --check`；不下载应用依赖，不运行 Flutter 测试或构建 EXE。 |
| 可逆、低影响的界面/配置改动 | 格式与适用的静态检查，复用能覆盖真实行为的现有测试；不写只复述实现的测试。 |
| 排版算法、输入事务、持久化、生命周期等逻辑改动 | 覆盖根因和重要失败边界的定向测试，加实际受影响的相邻契约；原生改动按技术规则完成相应编译或测试。 |
| 合并、推送、发布或支持能力升级 | 执行作者对此阶段要求的完整检查；本地依旧不跑作者已禁止的全量 Flutter 测试。需要真机证据的能力不能由单测替代。 |

- 先确定改动影响的路径，再挑验证。影响分析工具的候选清单须检查依赖关系，不能把共享文件或生成文件关联出的数百套件当作无条件执行队列；明确适用的强制检查仍须完成。
- 同一源码/配置/依赖状态、同一场景的通过结果可以复用。只有后续变化影响到覆盖结论，或出现新失败、未解决疑点时，才扩大或重跑验证；新提交哈希本身不是全量重跑理由。
- 一次只安排一个执行者运行同一工作区的 Flutter 测试，避免 native 资产锁和结果文件争用。记录真实退出码和执行数量；零执行、进程启动、没有新输出都不等于通过。
- 失败先区分代码断言、编译/装载、进程/缓存、审批/服务故障；不得将“可能是环境问题”写成通过，也不要为了无关基线问题扩大修复范围。未完成的必需检查如实记录，不宣称工程门全部通过。
- 格式、单测、native 编译、完整应用构建、真实游戏验收分别报告。自动测试绿不等于用户已验收；截图拟合成功不等于新台词、其他尺寸或其他游戏已适配。

## 6. 工作区与构建交接

- `upstream/develop` 只读获取；`custom` 是个人正式线；`origin/custom` 是正式远端；`codex/<任务名>` 是候选分支。不向 `upstream` 推送，不改写 `custom` 历史、不 force-push。
- 编辑前检查分支、工作区与未提交改动。不同任务使用独立 worktree；同一候选后续修订优先复用原 worktree。并发时记录本机 ownership，只修改自己的 claim。用户说工作区“作废”表示不再以它为依据，不自动授权删除文件或丢弃改动。
- 新 worktree 按作者规则先运行 `tool/setup_worktree.ps1`。纯文档或仅源码调查使用已有的 `-SkipBootstrap`；实际需要测试/构建时再初始化所需依赖。同一环境已就绪，不反复 bootstrap、clean 或下载。
- 默认由用户运行完整应用构建 BAT，以及开关 Fushi/游戏、转区启动、注入/附着和切到台词。代理负责源码、文档、必要的定向编译/测试与日志诊断。授权完成这些工作无需逐命令确认，工具要求的执行批准仍须遵守。
- 交接时一次给清目标提交/架构、工作区和 BAT/候选路径、操作顺序、预期、失败停止条件与日志位置。完整构建由用户执行时，先交源码候选与入口，构建产物确认后再称 EXE 已交付。
- 是否重编取决于实际构建输入；是否重启游戏或重新注入取决于实际加载对象与输入契约。文档修改不要求编译，应用侧修改也不自动要求重启游戏。没有变化时不让用户重复相同操作；不默认 clean。
- 用户“打开了/好了”只证明操作完成，验收状态须依据明确结果或证据。涉及迁移先核实备份、升级、降级与恢复，完成适用技术验证并在交接中说明结果；不绕过 schema/version 守卫打开旧数据。

## 7. 提交、采用与反馈

- 完成本轮后默认本地提交：先检查状态，只暂存本轮文件，执行暂存差异检查；不使用 `git add -A`，不夹带用户或其他任务的改动。
- **合入 `custom` 仍需用户明确授权采用；推送、正式构建、发布和向上游贡献分别以已有明确授权为准。**“继续修改”“帮我优化”“测试绿了”不自动等于采用或推送。作者的 PR 作者白名单不替代个人正式线验收门。
- 规则/文档候选不要求 EXE，给出可审阅的实际差异后再请求采用；普通授权内修改不要逐段索要确认。不要用本次规则编辑自动给本次合并授权。
- 已有授权可覆盖后续必要步骤时直接继续；确需询问时先准备好具体结果，说明将采取的动作以及未被覆盖的授权边界。应用、合并或发布前的批准应是最后一步，不能让用户先批准一份空计划。
- 回复先讲结果、用户下一步及重要限制，用中文和熟悉的词。简单任务几句话即可；提交/分支、工作区、验证与未完成项可用简短链接集中列出，不复制整段工具输出或反复讲同一计划。
- 如实区分“已写代码”“工程验证通过”“用户已验收”“已合并/推送”。没有必须由用户决定的事项就完成工作，不以“要不要我继续”收尾。

## 8. 换模型与保护已有成果

- 这些约束适用于所有模型。接手时先核对任务交接单中的分支、固定提交、当前差异和用户最新阶段；用几句话说明本批目标、修改范围、必须保持的行为和验证方式，然后继续已授权工作，不要求用户逐项批准。记录过期时先用源码与现有证据更新，不把摘要当作事实。
- 正式线、未验收候选和废弃方案分别标记。大批改动前保留可追溯的固定提交/检查点；检查点表示“能找回”，不等于“功能已验收”。不覆盖旧检查点，不清理其他任务工作区，不把全仓回退当作单项修复。
- 每批只解决一个明确目标及其必要相邻问题，不顺手更换架构、升级无关依赖、统一命名或删除看不懂的代码。发现需要扩大范围时先查明依赖并说明理由；在已有目标和授权内继续，涉及产品目标、持久数据风险或正式采用才询问。
- 用可观察的行为保护底子，不用“文件一律不能改”妨碍根因修复。相关测试验证旧场景仍成立，并加入当前问题的失败场景；禁止为过关删用例、跳过断言、随意放宽阈值或把错误吞成成功。预期确需改变时写清需求依据，同时审查生产改动与测试差异。
- 文案、文档和边界明确的局部实现按第 5 节做轻量检查。数据迁移、文本与画面归属、点击拦截、跨进程契约、生命周期或算法路线变化，在本批交付前集中做一次独立审查；审查者看实际 diff、测试和证据，不只看实现者总结。复用已通过的验证，不为审查再无条件全跑一遍。只有结论冲突、根因不明或需要路线决策时再升级模型，不默认每步使用高成本模型。
- 独立审查发现关键失败或必需证据不足时，保留候选并写明缺口；不得自行宣称已验收或合入正式线。独立审查也不能替代用户游戏体验。
- Git 只保护已提交源码；设置、数据库、校准样本、模型文件和运行产物分别看待。执行可能修改持久数据的操作前核对已有备份/隔离方式与兼容性，不删除用户样本来“恢复正常”，不承诺退回旧 EXE 就能恢复数据。
- 每批结束只维护一份短交接单：准确基线、当前阶段、已确认事实、未解决项、验证证据位置和下一步。暂时性模型禁用、审批故障、截图路径等写任务记录，不重复散落进长期规则。

规则文档是协作约束，不是操作系统权限隔离。分支、worktree、检查点、实际测试和正式采用边界共同降低误改风险；不要宣称已经安装未实现的自动拦截或远端分支保护。
