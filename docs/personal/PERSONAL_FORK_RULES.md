# Fushi 个人工作规则

本文件只放个人协作约定；技术、数据与验证细节以根 `CLAUDE.md` 和 `docs/agent/` 为准。当前进度与证据写任务记录，不写这里。

## 1. 范围

- 这是 Fushi（原 Hibiki）的 Windows 个人版本：跟进作者更新，优先复用现有实现；上游有等价能力时缩减个人重复代码。
- 作者规则里的“小改默认合并”“验证后 push/PR”在本项目不生效，按第 6 节执行，无需每次再问。
- 交付默认只做 Windows，Galgame 严守 Windows-only。引用第三方实现先核实许可证与分发义务。密钥、私人路径、游戏素材和远程设备信息只放被忽略的本机文件。
- 旧聊天、任务书、交接单里的版本和结论要用当前源码与证据核对后再用。

## 2. 先识别用户意图

| 用户说 | 代理做 |
| --- | --- |
| “解释一下”“你看一下”“你觉得呢”“先别动” | 大白话解释或给出带推荐的判断；只读调查，不改源码、不构建。 |
| “先记下”“全部测完再一起解决” | 记进当前任务的同一问题清单（现象、预期、证据），体验结束后统一归因，不逐条开工。 |
| “开始改”“按你说的改”“帮我做好” | 完成调查、实现、定向验证和本地提交，不反复确认普通实现细节。 |
| 工作中补充意见或问进度 | 纳入当前任务，简短回应后继续。 |

授权在同一会话内持续有效，不因重试、换模型或上下文整理而失效。

## 3. 批次与交接

- 按“集中体验 → 汇总问题 → 核实根因 → 统一修改 → 定向验证 → 一个候选”推进；问题按 `tool/bug.dart` 登记，未复现如实标注。阻断测试或损坏数据的问题先说明影响。
- 候选失败在原任务分支和 worktree 继续修，不为每个问题另起工作区。不要每修一处就让用户重编、重启或重新附着。
- 完整应用构建 BAT、开关 Fushi/游戏、转区、注入/附着、切台词由用户做；代理负责源码、文档、定向编译/测试和日志诊断。
- 交给用户构建时先提交，再一次说清：目标提交、要运行的 worktree BAT（已提交候选会自动在 `.worktrees/_candidate-build` 编译）、操作顺序、预期、失败停止条件。编译失败时代理自己读该目录下 `.build-cache/launcher-logs/last-failure.log`，不让用户复制输出。是否需要重编、重启游戏或重新注入，按实际变化的构建输入和加载对象判断，不默认 clean。
- 用户说“好了/打开了”只代表操作做完，不等于验收通过。

## 4. 模型分工

主代理负责根因、设计、整合和复核；边界清楚、能独立推进的辅助工作才派发，几行修改直接做。同一文件、同一验证只交一个执行者。只有结论冲突、根因不明或需要路线决策时才升级到高成本模型。

| 用途 | Codex | Claude Code |
| --- | --- | --- |
| 常规辅助子任务 | `gpt-5.6-luna`，`max` | `sonnet` |
| 纯检索、定位 | 同上 | `Explore` 代理 |
| 第 7 节的独立审查 | 与实现者不同的新代理 | 新开 `opus` 代理 |
| 首选模型服务不可用 | 改用 `gpt-5.6-terra`，不必再问 | 改用另一可用模型，不必再问 |

## 5. 验证

| 改动 | 本地验证 |
| --- | --- |
| 纯文档、规则、注释 | 核对引用和链接，`git diff --cached --check`；不下依赖、不跑 Flutter、不构建 EXE。 |
| 低影响界面/配置 | 格式和静态检查，复用能覆盖真实行为的现有测试。 |
| 算法、输入、持久化、生命周期 | 覆盖根因和重要失败边界的定向测试，加受影响的相邻契约。 |
| 合并、推送、发布、支持升级 | 作者要求的完整检查（本地仍不跑全量 Flutter 测试）；需真机证据的不能用单测代替。 |

- 影响分析工具列出的候选套件要看依赖关系再挑，不当成无条件执行队列。同一状态下已通过的结果直接复用，只有新变化、新失败或未解疑点才重跑。
- 状态分开报告：已写代码 → 工程验证通过 → 用户已验收 → 已合入/推送。测试绿不等于用户验收；一个截图拟合成功不等于其他台词、尺寸或游戏已适配。

## 6. 分支、提交与采用

- `upstream/develop` 只读；`custom` 是个人正式线（远端 `origin/custom`）；候选分支用 `codex/<任务名>`。不向 upstream 推送，不改写 `custom` 历史，不 force-push。
- 每个任务一个 worktree；并发时在 `.worktrees/coordination/claims/` 登记并只改自己的 claim。本地提交只暂存本轮文件，不用 `git add -A`。
- **合入 `custom` 需要用户明确同意；推送、正式构建、发布、向上游贡献各自单独授权。**“继续改”“测试绿了”都不算同意。请求批准前先准备好可审阅的实际差异。
- 清理 worktree：候选合入或用户宣布作废后，列出待清理项并注明是否已合入、有无未提交改动或本机证据（`.codex-test/`、校准样本）；用户确认后再删，claim 移到 `done/`。有未合入内容的只报告不删；`_candidate-build` 是编译缓存，不在清理范围。
- 回复用中文，先讲结果、用户下一步和重要限制；简单任务几句话。没有必须由用户决定的事就把活做完，不以“要不要我继续”收尾。

## 7. 保护已有成果

- 接手或换模型时，先核对交接单里的分支、固定提交、当前差异和用户所处阶段，再继续已授权工作。
- 每批只解决一个目标及其必要相邻问题，不顺手换架构、升级无关依赖、统一命名或删除看不懂的代码。大改前留检查点提交；检查点只表示能找回，不表示已验收。
- 不为通过测试而删用例、跳断言或放宽阈值；预期确需改变时写清依据。
- 数据迁移、文本/画面归属、点击拦截、跨进程契约、生命周期或算法路线变化，交付前做一次独立审查（第 4 节），审查者看实际 diff 与证据；发现关键缺口就保留候选、写明缺口，不宣称验收或合入。
- Git 只保护已提交源码。动数据库、设置、校准样本、模型文件前先确认备份与兼容性；不绕过 schema/version 守卫打开旧数据，不删用户样本来“恢复正常”。
- 每批结束只维护一份短交接单：基线、阶段、已确认事实、未解决项、证据位置、下一步。
