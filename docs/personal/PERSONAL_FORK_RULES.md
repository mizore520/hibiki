# Fushi 个人工作规则

只保存长期协作约定。技术契约见根 `CLAUDE.md` 与相关模块；进度、命令输出、候选证据和临时环境故障放在对应任务记录。

## 1. 范围与优先级

- 系统、开发者及用户当前明确指令优先。技术、安全、数据和平台约束由作者文档维护；本文件决定个人协作节奏、验证范围及正式采用授权。按职责解决表面冲突，只有无法同时满足的实质冲突才询问。
- 个人交付默认 Windows，Galgame 严守 Windows-only。保留作者更新与个人需求；优先复用现有及已知上游能力，只在缺少必要信息时扩大调查，不为每次小改搜索上游计划或全仓历史。
- 上游有更好的等价实现时缩减个人重复代码。第三方代码或资源须核对许可证与分发义务；密钥、私人设备/游戏路径和素材只放被忽略的本机文件。

## 2. 意图与完成范围

- 讨论和解释先给结论；用户要求“只记录”“全部测完再改”时，在同一问题清单收集现象与证据，不逐条实施。
- 明确行动请求授权必要调查、实现、定向验证与本地提交。自行决定可逆实现细节，持续完成这段范围；补充意见和进度询问不自动取消原任务。
- 只有缺失答案会改变关键产品目标、数据风险或授权范围时才提出具体问题，同时推进不依赖答案的工作。已有授权跨重试、换模型和上下文整理继续有效。
- 大任务按可体验能力分阶段，写清本批目标、验收场景和结束条件。同批反馈统一归因、修改、验证后交一个候选；失败继续在原任务分支修，不为每个问题另起工作区。

## 3. 工作区与数据

- `upstream/develop` 只读获取；`custom` 是正式线，`origin/custom` 是正式远端，`codex/<任务名>` 是候选分支。不向 `upstream` 推送，不改写 `custom` 历史，不 force-push。
- 编辑前核对分支、差异与已有 worktree。所有修改在独立 worktree 中完成；同一候选优先复用原工作区，不覆盖、清理或擅自提交他人改动。“作废”不授权删除工作区。
- 只读调查与纯文档改动不初始化应用依赖或复制密钥。需要测试/构建时按根规则准备环境，已就绪则复用；不默认 bootstrap 或 clean。
- 并发任务在主 checkout 的 `.worktrees/coordination/claims/` 记录分支、基线、文件范围与执行者，只编辑自己的 claim；集成工作由明确的 owner 收口。
- Git 只保护已提交源码。持久数据操作须核对备份/隔离、升级、降级与恢复；不绕过 schema/version 守卫，不删除用户样本来掩盖问题，不承诺旧 EXE 能自动恢复数据。

## 4. 委派与模型

- 仅在子任务边界清楚、可独立推进、收益超过交接成本，且主代理有其他工作可做时委派。几行修改直接完成，不为凑数量拆任务或多层转派。
- 常规辅助任务优先 `gpt-5.6-luna` / `max`；服务不可用时可换 `gpt-5.6-terra`，强度按任务选择。让已经工作的代理做完，不为模型恢复重派；代码断言失败先查事实。
- 主代理负责关键判断、根因和整合。给子代理目标、文件范围、相关约束与验收标准，不传无关历史；同一文件或验证只安排一个执行者，依据实际差异和证据复核，不全部重做。
- 不无界重试服务/审批故障，也不绕过审批；保留进度并完成未受阻工作。工作模型与自动审批服务是不同设置，不声称工具未实际完成的配置变更。

## 5. 验证

- 文档、规则、注释只做内容、引用与差异检查，不跑 Flutter 测试或构建 EXE。可逆的低影响 UI/配置修改使用格式、适用的静态检查及有效的已有测试，不新增复述实现的测试。
- 逻辑修复覆盖根因、重要失败边界和实际相邻契约；可复用有效回归用例，`docs/BUGS.md` 的测试记录写清覆盖证据。原生、迁移、跨进程契约和支持能力升级须完成各自技术门槛。
- 通过结果在源码、配置、依赖和场景仍适用时复用；只有新变化、失败或未解决疑点才重跑/扩大验证，新提交哈希本身不是理由。影响分析工具给的是候选清单，按真实依赖选取；适用的明确强制检查仍须完成。本地不跑全量 Flutter 测试。
- 同一工作区的 Flutter 测试串行安排。以真实退出码、实际执行数量和目标 suite 是否完成判定；编译/装载失败或零执行不算通过。先区分断言与环境故障，不靠重复碰运气或放宽断言过关。
- 数据迁移、文本/画面归属、点击拦截、跨进程契约、生命周期或算法路线变动，在本批交付前集中做一次独立审查，审查实际 diff、测试和证据；普通局部修改无需机械增加审查轮次。
- 自动测试、定向编译、完整应用构建和真实游戏验收分别报告。用户可见修复需原始案例验证；截图拟合成功不能证明新台词、其他尺寸或其他游戏都适配。必需证据不足时保留候选并说明缺口。

## 6. 构建与真机交接

- 默认由用户运行完整应用构建 BAT、开关 Fushi/游戏、转区启动、注入/附着和切到台词；代理负责源码、定向编译/测试与日志诊断。用户明确授权代理操作时按范围执行，无需逐命令重新确认。
- 交接一次给清目标提交/架构、工作区、BAT 或候选位置、验证场景、预期、日志位置及失败停止条件。用户负责完整构建时，先交源码候选和入口，产物确认后再称 EXE 已交付。
- 是否重编取决于构建输入，是否重启或重新注入取决于加载对象和输入契约。没有变化不要求重复操作，应用侧修改不自动要求重启游戏。
- “打开了/好了”只证明操作完成，验收须依据明确结果或证据。官方更新器更新作者软件包；个人源码通过 Git 整合后重新构建。

## 7. 提交与采用

- 完成本轮默认本地提交：检查状态，只暂存本轮文件（不用 `git add -A`），运行 `git diff --cached --check`；提交后确认状态。
- 合入 `custom` 需用户明确授权采用；推送、正式构建、发布和向上游贡献分别以已有明确授权为准。作者的“小改默认合并”、PR 白名单或测试通过均不替代此门，也不允许向 `upstream` 推送。
- 文档/规则采用以实际差异审阅代替 EXE 验收；编辑规则本身不授权本次合并。确需批准时先准备好可审阅结果，再说明尚缺的具体授权。
- 回复用中文先说结果，简述提交/工作区、实际验证和重要限制；按需给候选入口。区分已实现、已验证、已验收与已合并/推送，不套固定长报告，不以“要不要继续”结束已授权工作。

## 8. 接手与保护成果

- 换模型或接手未完成任务时，核对任务记录的分支、固定提交、当前差异和用户最新阶段，再继续已授权范围。内嵌查词有 `GAL_LOOKUP_HANDOFF.md` 时从它进入，否则使用当前候选的任务记录；旧摘要不代替事实。
- 正式线、未验收候选和废弃方案分别保留；大批修改前留可追溯检查点，不以全仓回退代替单项修复。检查点不是验收证明。
- 每批只处理明确目标及必要相邻问题，不顺手换架构、升级无关依赖或改名。用可观察的旧行为和失败场景保护成果，不靠“文件一律不能改”妨碍根因修复；预期确需变化时说明需求依据。
- 只维护一份短交接记录：基线、阶段、已确认事实、未解决项、证据位置和下一步。规则文档不等于操作系统隔离或自动拦截，不能宣称未实现的保护。
