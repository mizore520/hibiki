## BUG-2738 · KiriKiri 查词弹窗上滚动滚轮会让游戏翻到下一句
- **报告**：2026-09-27（用户：《王様恋愛》Ver1.00 / KiriKiri Z，打开游戏内查词后想用滚轮往下看词典，游戏直接翻到下一句）
- **真实性**：✅ 真 bug（静态证据 + 日志，未实机复验）。用户当次 `hibiki_glookup.log` 里多次卡片在没有任何点击记录的情况下被 dismiss（如 23:30:46 seq=5、23:30:52 seq=7），与「台词变了、查词随之收起」一致。游戏 exe 内含 `tTVPWheelDirectInputDevice`，`-wheel` 选项 `"value":"dinput"` 标 `"default":true`：KiriKiri 默认经 DirectInput 读滚轮。宿主 `low_level_mouse_hook.cpp` 在光标压在卡片上时吞掉 `WM_MOUSEWHEEL` 并转投 WebView，但 WH_MOUSE_LL 挡不住 DirectInput，同一格滚轮仍经 `Window.onMouseWheel` 到达 KAG；而直连路由下卡片是宿主的 WebView2 窗口，游戏内 `fushiLookupMouseWheelHook` 只认 TJS 卡片层（`fushiLookupCardSeq`），不知道它的存在，于是放行翻页。通用输入护盾的 DirectInput 设备 hook 依赖在游戏建设备之前装上工厂 hook，附着场景常来不及，且只管左键。
- **[x] ① 已修复** — `kirikiri_adapter.inc`：DLL 每帧（传感器已活后）用 Win32 判定光标下的顶层窗是否为「别的进程、可见、owner 属于本进程」的窗口，即宿主贴在游戏上的浮窗（直连查词卡片、Hook 工具条、悬浮歌词），仅在变化时写 `global.fushiLookupHostOverlayUnderCursor`；bootstrap 先把它初始化为 0；`fushiLookupMouseWheelHook` 在卡片判定之前据此消费滚轮。滚轮无论来自 DirectInput 还是窗口消息都在 `onMouseWheel` 汇合，所以在这里消费覆盖两条来源。判据只用 Win32 窗口归属，不认游戏或宿主私有标识。
- **[x] ② 已加自动化测试** — `native/galgame_hook/tests/kirikiri_lookup_source_guard_test.py` `find_host_overlay_wheel_leak`：滚轮 hook 必须先看浮窗标记再判卡片、bootstrap 必须初始化该全局、每帧泵必须同步；`test_host_overlay_wheel_gate_mutations_are_red` 对真实适配器逐项删除三者，规则都会变红。Win32 判定与 DirectInput 时序没有行为级测试，需实机复测。
- **备注**：光标刚移到卡片上的同一帧内滚动，最多有一格滚轮在标记更新前漏给游戏。
