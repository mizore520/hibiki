# 审查与回归记录

适用于用户要求审查的范围；不因出现“审查”一词自动扩大成全项目或无限持续任务。

## 一次性与持续审查

- 一次性代码/规则审查直接返回有证据的发现；按用户给定范围和实际风险安排阅读，无需套固定模块顺序或创建日报。
- 用户要求持续审查或持久化报告时，维护一份 `docs/reviews/YYYY-MM-DD-project-review.md`（或指定记录），追加范围、发现、证据及尚未覆盖项，不覆盖历史；需要后续轮次时才写下一轮范围。
- 纯审查不改业务代码；用户已授权“审查并修复”时继续完成范围内修复、定向验证和本地提交，不另设一次批准。
- 区分源码风险、已复现 bug、已验证修复。发现要说明真实触发条件和影响；未运行的验证不能写成通过。复核修复时检查相应差异与证据，按新变化决定是否需补跑，不机械从头审全仓。

## 回归记录

- 正在执行安装包/设备回归任务时，将确认的回归与状态保留在本地 `docs/REGRESSION_BUGS.md`（忽略、不入库）或任务已指定的清单，避免重复维护多份记录。
- 后续测试先挑与本次改动和场景有关的 open 项；全套验收仅在用户授权该范围时执行。用户集中体验阶段按个人规则先收集，不逐条修复/重建。
- 截图和运行日志放 `.codex-test/`，记录可核对的证据位置；登记项目 bug 时遵守 [Bug 文件约定](../BUGS.md)。只读审查不为虚构运行证据创建文件。
- 设备证据格式按需查 [集成测试](integration-testing.md)，自动检查不替代用户验收。
